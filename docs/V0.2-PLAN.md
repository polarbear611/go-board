# GoSandbox V0.2 开发计划与测试方案

> 基线：V0.1（commit `0934de0`）。两大功能：**题目保存/加载**（FastAPI + MySQL）、**正式对弈 + 自动数目**。

---

## 1. 架构总览

```
┌─────────────┐   /api/*    ┌──────────────────┐      ┌─────────────┐
│  React SPA   │ ─────────▶ │  FastAPI 微服务   │ ───▶ │  <mysql 容器>  │
│ (静态, nginx) │  同源代理   │ go-board-web:8000 │      │  库 go_board │
└─────────────┘            └──────────────────┘      └─────────────┘
        ▲                            ▲
        └── nginx (<nginx 容器>) ───┘  均在外部网络 <docker 网络>
```

- 前端：现有 React SPA，保存/加载改调同源 `/api/*`。
- 后端：FastAPI + SQLAlchemy + PyMySQL，独立 docker-compose 项目，对齐服务器现有 `<另一个内部项目>` 范式。
- 数据库：现有 `<mysql 容器>` 新建库 `go_board`。

## 2. 里程碑拆解（每步独立可验收）

### M1 前端重构：初始局面分离 + 保存/加载（localStorage 临时版）
**目标**：把「题目初始局面」从「试下棋盘」中分离，先用 localStorage 跑通保存/加载交互，不依赖后端。

改动：
- `useBoardStore`：新增 `problemSetup`（`{ stones, firstPlayer }`），`IMPORT_STONES` / 手动确认时写入；试下落子只动 `stones`，不动 `problemSetup`。
- 新增 `SAVE_PROBLEM` / `LOAD_PROBLEM` 概念（数据访问先封装在 `src/api/problems.js`，localStorage 实现）。
- UI：试下前「保存题目」按钮 → 弹窗输入题号 → 确认；「加载题目」入口 → 题号列表 → 选择载入。

**验收**：摆好棋形 → 保存为「第235题」→ 刷新页面 → 加载「第235题」→ 局面还原；试下若干手后再次加载，回到干净初始局面。

---

### M2 后端 + DB：保存/加载落库
**目标**：把 `src/api/problems.js` 从 localStorage 切到真实后端，数据进 MySQL，跨设备共享。

后端（`backend/`，FastAPI）：
- `model`：`problems(id, problem_no UNIQUE, black_stones JSON, white_stones JSON, first_player, created_at, updated_at)`
- 接口：
  - `POST /api/problems` 保存/覆盖（按 `problem_no` upsert）
  - `GET /api/problems` 列表（题号 + 时间）
  - `GET /api/problems/{no}` 取单题
  - `DELETE /api/problems/{no}` 删除（可选）
- `Dockerfile` + `docker-compose.yml`：挂外部网络 `<docker 网络>`，连 `mysql:3306`。

部署：
- <mysql 容器> 建库 `go_board` + 授权。
- `go-board.conf` 加 `location /api { proxy_pass http://go-board-web-1:8000; }`。
- 前端 `problems.js` 改为 fetch `/api/*`。

**验收**：A 浏览器保存题目，B 浏览器（或手机）加载列表能看到并载入；服务器重启后数据仍在。

---

### M3 对弈增强：pass + 终局 + superko
**目标**：黑白可按完整规则正式对弈。

改动：
- `useBoardStore`：新增 `PASS` action；记录 `passCount`；连续两次 pass → 进入 `phase: 'scoring'`（终局）。
- `goRules`：ko 升级为**完整 superko** —— 维护历史局面集合（局面字符串哈希），落子后若局面曾出现则非法，杜绝多劫循环 / 长生。
- UI：对弈模式下显示「虚手」按钮、当前手数、双方提子；终局提示。

**验收**：完整走一局，pass 正常；构造单劫、三劫循环场景不死循环、不允许同形再现；双 pass 后进入终局态。

---

### M4 算目：标记死子 + 中国规则数子
**目标**：终局后自动计算双方目数并判定胜负。

改动：
- 终局 `scoring` 阶段进入「标记死子」子模式：点击某块 → 整块标记为死（视觉变灰），可反复切换。
- 数子算法（中国规则）：
  - 死子从棋盘移除（归还为对方地）。
  - 每方得分 = 己方活子数 + **仅被己方包围**的空点数。
  - 双方都能到达的空点为单官（不计）。
  - 贴目可配置（默认中国规则黑贴 3¾ 子 = 7.5 目）。
- UI：终局面板显示「黑 X 子 / 白 Y 子 / 黑胜 N 子」。

**验收**：构造 3~4 个已知终局棋形，数子结果与手工计算完全一致；死子标记能正确改变归属。

## 3. 测试方案

### 3.1 前端单元测试（Vitest）
新增 `vitest` + `src/utils/goRules.test.js`，覆盖纯逻辑：

| 用例 | 断言 |
|---|---|
| 提单子 | 落子提走 1 颗无气子，`captured===1` |
| 提整块 | 提走多子连通块 |
| 自杀禁手 | 无气落子返回 `{valid:false, reason:'suicide'}` |
| 提子后有气则合法 | 边角扑提 |
| 单劫禁手 | 立即回提返回 `reason:'ko'` |
| superko | 同形再现被拒（M3） |
| 数子-纯空盘分割 | 地域计数正确（M4） |
| 数子-含死子 | 标记死子后归属翻转（M4） |

### 3.2 后端测试（pytest，M2）
- `POST` → `GET {no}` 往返一致。
- 重复 `POST` 同题号 → upsert 覆盖而非报错。
- `GET` 列表数量正确。
- 不存在题号 → 404。

### 3.3 手动验收清单
每个里程碑结束跑一遍对应「验收」段落 + `npm run build` 通过 + 部署 smoke（M2 起）。

---

## 4. 推进与验收节奏

1. 每个里程碑独立成一个 / 多个 commit，完成后 `npm run build` + 跑测试 + 演示验收点。
2. 验收通过后再进入下一里程碑；不通过则当场修。
3. M2、M4 完成后各 tag 一次（`v0.2-m2`…），M4 全部通过后发布 `v0.2`。

---

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 自动判死子不可靠 | 不做自动判死，改人工**标记死子**（已与用户确认） |
| 后端连 MySQL 网络/权限 | 对齐 <另一个内部项目> 现成范式，复用 `<docker 网络>` 网络 |
| API key 暴露 | M2 起识别接口也可迁到后端代理（顺带解决） |
| 数子规则争议 | 采用中国规则数子（比数目实现简单、争议少） |
